# Аудит інтерфейсу Minecraft Java 26.2

Статус: аудит для погодження. Дизайн-кит, ескізи та реалізація ще не розпочаті. Код, ресурси мода, налаштування гри й попередні матеріали флакона не змінені. Створено лише цю папку аудиту. Комітів немає.

## 1. Що перевірено

- Проєкт справді використовує Minecraft **26.2**, Fabric API **0.158.0+26.2**, Java 25. Перевірено `gradle.properties`, конфігурацію Loom, клієнтський код і локальний оригінальний клієнтський JAR.
- `version.json` усередині JAR: стабільний реліз 26.2, resource pack **88.0**, дата складання 2026-06-16. Контрольна сума JAR та лічильники записані в [provenance.json](provenance.json).
- Знайдено **555 GUI PNG**, з них **466 GUI-спрайтів**, а також **40 іконок ефектів**. Виявлено 44 GUI metadata з `nine_slice`. У [resources.tsv](resources.tsv) наведено точний шлях кожної текстури, розмір PNG, належність до GUI-атласу, параметри GUI scaling і SHA-256.
- [resource-paths.md](resource-paths.md) містить повний перелік реальних шляхів, включно з ресурсами меню, які зараз лише обліковуються. Це інвентаризація, а не перелік уже дозволених змін.
- Перевірено байткод ванільного рендера через `javap`, зокрема `Hud`, `GuiGraphicsExtractor`, контекстні смуги, контейнери, підказки, чат, Tab і субтитри. Локальні докази: [render-bytecode.txt](render-bytecode.txt).
- Перевірено джерела встановленого Fabric API: реєстр HUD, реєстр висот, вбудовані resource packs. Докази: [fabric-api-evidence.txt](fabric-api-evidence.txt).
- Збережено [перелік 153 верхньорівневих класів екранів](screen-classes.txt): 128 у клієнтському пакеті GUI та 25 у Realms. Допоміжні класи й абстрактні основи не є окремими екранами для дизайну.
- Context7: виконано пошук Fabric та запит документації. Видача підтвердила сучасні `GuiGraphicsExtractor` і текстурний фон контейнера; точні шляхи й 9-slice перевірено безпосередньо в JAR 26.2, оскільки видача Context7 не містила повної інвентаризації.

Офіційні зовнішні джерела: [реліз 26.2](https://www.minecraft.net/en-us/article/minecraft-java-edition-26-2), [рендер HUD](https://docs.fabricmc.net/develop/rendering/hud), [малювання GUI](https://docs.fabricmc.net/develop/rendering/gui-graphics), [HudStatusBarHeightRegistry для 26.2](https://maven.fabricmc.net/docs/fabric-api-0.155.2%2B26.2/net/fabricmc/fabric/api/client/rendering/v1/hud/HudStatusBarHeightRegistry.html). Останнє посилання — на доступну вебдокументацію 0.155.2; остаточні висновки щодо встановленої 0.158.0 звірені з її локальними джерелами.

## 2. Що показує наданий скрін

На скріні є два ряди сердець, частково заповнена їжа, рівень 7, XP, хотбар і синій флакон праворуч. Це обрізаний фрагмент, тому він не встановлює роздільну здатність вікна чи GUI Scale. Відтворювати з нього Scale 2/3 як нібито виміряний розмір не можна.

Флакон значно насиченіший і деталізованіший за ванільні серця та рамку хотбара. Потрібні споріднені матеріали, контур і світлотінь, але дрібні іконки не повинні успадковувати всю деталізацію великого флакона. Права частина має більшу візуальну вагу. Порожній декоративний флакон ліворуч не пропонується: баланс слід перевіряти масою рамок, відступами та наявним слотом другої руки, включно з випадком, коли той порожній.

Флакон уже затверджений і залишається візуальним еталоном. Дизайн трьох концептів має працювати з ним без повторного редизайну флакона. Збережена гравцем позиція флакона й режим шульги також мають працювати.

## 3. Чи вистачить заміни ресурсів

**Для статичного оформлення більшості іконок, рамок, підказок і фонів — так. Для всього завдання — ні.**

| Спосіб | Що дозволяє | Межа |
|---|---|---|
| **С** — заміна GUI-спрайтів | Змінити матеріал, форму всередині ванільного прямокутника, контур, усі вже наявні стани | Не змінює координати, алгоритм заповнення, колір тексту чи умови видимості |
| **Т** — заміна окремої текстури | Перемалювати фон контейнера зі збереженням UV і слотів | Ці фони не стають GUI-атласом від додавання `.mcmeta` |
| **Ф** — клієнтський Fabric HUD API | Динамічний акцент, інше подання значення, нова геометрія та реакція на стан | Потрібно зберегти всі ванільні умови й узгодити висоти з іншими HUD |
| **Е** — інтеграція клієнтського екрана | Наші екрани B, колесо, книга, редактор; за потреби погоджені зміни ванільних екранів | Загального resource pack недостатньо для зміни довільного кольору тексту чи поведінки віджетів |

Ресурс мода може перевизначати `minecraft:`. Для прикладу, реальний шлях `assets/minecraft/textures/gui/sprites/hud/hotbar.png` перекриває ванільний хотбар. У `assets/mysteries_above/...` лежатимуть власні спрайти, на які має посилатися наш рендер; самі собою вони ванільні ресурси не замінять.

Рекомендований механізм майбутнього перемикача — вбудований вимиканий resource pack через `ResourceLoader.registerBuiltinPack`, із `PackActivationType.DEFAULT_ENABLED`, та умовна клієнтська гілка для погодженого власного HUD. Вимикання відновлює нижчий шар ресурсів, включно з обраним гравцем стороннім resource pack. Не слід класти обов'язкові перевизначення `minecraft:` у базові ресурси мода, якщо їх потім неможливо вимкнути пунктом на B.

Перемикання pack потребує перезавантаження ресурсів; це не безкоштовна миттєва заміна PNG. Флакон і власні екрани не повинні втрачати свої обов'язкові ресурси разом із вимкненням оформлення ванілі. Це архітектурна пропозиція, ще без реалізації.

### Важливі обмеження

1. **Динамічний колір шляху не задається статичним PNG.** Потрібен нейтральний шар для tint і малий рендер акценту. Для HUD це можна зробити через Fabric, без міксинів. Не слід заново малювати предмети, якщо достатньо поверх ванільної рамки намалювати акцент у тих самих координатах.
2. **Велике здоров'я, трубки Б і компактна форма В змінюють подання/логіку.** Для них потрібні `HudElementRegistry.replaceElement` і, якщо змінюється висота, `HudStatusBarHeightRegistry`. API має окремі `HEALTH_BAR`, `FOOD_BAR`, `ARMOR_BAR`, `AIR_BAR`, `MOUNT_HEALTH`, `INFO_BAR`, `EXPERIENCE_LEVEL`. Реєструвати слід один раз, перемикач читати під час вибору гілки; реєстр висот після запуску заморожений.
3. **Не кожна панель — спрайт.** Чат, scoreboard, Tab, субтитри, частина текстових підкладок малюються прямокутниками/текстом. Шляхи на кшталт `hud/chat_background.png` чи `hud/scoreboard.png` у 26.2 відсутні. Ресурсами можна оформити їхні наявні іконки; для нової панелі потрібна окремо погоджена зміна композиції. Переписувати чат цілком заради рамки недоцільно.
4. **Темне тло й ванільні темні написи контейнерів конфліктують.** `AbstractContainerScreen.extractLabels` та `InventoryScreen.extractLabels` використовують `0xFF404040`. Ресурсами цей колір не змінити. У дизайн-киті треба спершу перевірити світлішу вставку під заголовком; альтернативне світле письмо потребує окремого клієнтського втручання. Глобальне перехоплення всього тексту неприйнятне для сумісності.
5. **Усе в одному атласі та лише ресурсні заміни несумісні для старих фонів контейнерів.** `textures/gui/container/*.png` малюються прямим `blit`, а не `blitSprite`. Буквальне виконання вимоги атласу для цих фонів потребує зміни їхнього виклику малювання. У наступних етапах треба погодити один із двох конкретних варіантів: залишити ванільні окремі фони як виняток або окремо дозволити їхнє переведення на атлас зі збереженням координат. Зараз жоден варіант не впроваджено.
6. **Глобальні віджети перетинають етапи.** Заміна `widget/button*.png`, `widget/slider*.png`, загальних полів/вкладок змінить і головне меню, паузу, налаштування, а також моди, що їх використовують. До окремого рішення щодо етапу 3 глобальне перевизначення цих спрайтів не входить у реалізацію. На наших екранах застосовується власний кіт; ванільні спільні віджети на етапі 2 слід або лишити, або показати конкретну пропозицію вибіркового оформлення.
7. **Приціл має особливий pipeline `CROSSHAIR`.** Золотий PNG не гарантує видимого золотого кольору на екрані. Базовий ескіз має зберігати ванільну контрастну поведінку; справжній кольоровий приціл означав би окремо погоджену зміну рендера.

Жодної необхідності нових міксинів для базового статичного HUD наразі не виявлено. Можливі складні зміни екранів ще не доведені як такі, що потребують міксину; спершу ресурси, наявні компоненти й Fabric hooks. Не можна обіцяти «все без міксинів», доки не вибрані композиція та варіант для старих фонів.

## 8. Велике здоров'я й три майбутні концепти

Це вимоги до порівняння, а не вибір дизайну замість користувача.

- **А, дискретні іконки:** максимально ресурсний шлях; звичайні й багаторядні серця читаються по-ванільному. Самою текстурою неможливо обмежити довільне зростання кількості рядків. Треба показати, де починається проблема висоти.
- **Б, трубки:** змінює площу й спосіб читання. Потрібні впізнавані червоне/тепле/сталеве/блакитне, половини/точне число, absorption окремо, стани poison/wither/frozen/hardcore. Якщо трубки виходять за ванільний резерв, показати зачеплені offhand/attack/flask/mod HUD.
- **В, гібрид:** кандидат для обмеженої висоти при високому максимумі, але поріг/число не обирати непомітно. На ескізі порівняти звичайні ряди й компактне подання «поточне / максимум» з окремим absorption та знаком стану.

Майбутня матриця HP: 20, 40, 100, 200, 1000 максимуму; половина серця, майже нуль, нуль absorption і великий absorption; різний max HP під час гри. Значення в компактній формі не округлювати так, щоб ненульове здоров'я виглядало нульовим. Число тисяч не може розсувати слоти хотбара.

Пороги/анімація контекстності ще не затверджені. У благополучному стані приглушується оздоблення; критичні іконки, порожня шкала, число й знак стану не повинні зникати. Зміна кольору не є єдиним сигналом. Власний renderer має зберігати ванільний пріоритет poison/wither/frozen і коректне поєднання hardcore/absorption/regeneration, а не лише дев'ять ізольованих прикладів.

## 9. Дизайн-кит: наступний окремий результат

Після погодження цього аудиту підготувати лише короткий кіт, перед ескізами HUD:

1. Палітра матеріалів і семантичні палітри HP/food/air/armor; приклади на світлому/темному/сніжному тлі.
2. Панель під 9-slice: кути, 1 GUI px золота, темний зовнішній контур, легка тінь, непрозорість центра; точні borders та мінімальний розмір.
3. Слот із незмінним 16×16 предметом і наявними ванільними межами.
4. Кнопка: normal/hover/focus/disabled/selected; tooltip background/frame, divider, scrollbar/slider primitives.
5. Правило акценту від PathwayBranding, читабельний варіант на темному, один fallback; XP/selected-slot/невеликі деталі, без перефарбування семантичних шкал.
6. Шрифт: базово залишити ванільний; перевірити «і ї є ґ І Ї Є Ґ», цифри, знак мінуса/дробу, довгі українські фрази. Власний шрифт не потрібен без доведеної користі.
7. Приклади застосування тих самих primitives до B, кола здібностей, книги й редактора. Окремі художні поверхні книги можуть лишатися, але рамка, текст, контролери й стани мають належати одному кіту.

9-slice у 26.2 підтверджений, зокрема у `widget/button.png.mcmeta` (200×20, border 3), `tooltip/background.png.mcmeta` (100×100, border 9). Ці ванільні borders — технічні приклади, а не вже обрані параметри нового кіту. Малі фіксовані HUD-іконки не потребують 9-slice.

## 10. Матриця ескізів і перевірок

На стадії ескізів:

| Вимір | Що саме показати |
|---|---|
| Фон | Наданий скрін; повний кадр на світлому тлі, у печері, на снігу; додатково перевірити небо/пісок |
| Розмір | GUI Scale 2 і 3 у справжніх екранних пікселях, без автозменшення сторінкою; окремо crop ×4 nearest із підписом, від якого зображення він збільшений |
| Умови кадру | Підписати viewport/роздільну здатність, effective GUI scale, джерело фону. Синтетичний фон/композит явно позначити; не називати його тестом у грі |
| Концепти | А, Б, В з одним і тим самим флаконом і запасом під offhand/attack; баланс при повній та порожній offhand, обидві руки |
| Стани | Повне; low HP; голод; underwater/low air; poison; wither; absorption; hardcore; високий max HP. Додатково frozen, regeneration/blink і mount/jump/locator, щоб не загубити стани 26.2 |
| Екрани | E та одна скриня; B, його налаштування з перемикачем стилю, drag editor |

Усе це — після окремого погодження кіту. Для наданого обрізаного скріну можливий лише чесно підписаний композиційний crop; для перевірки GUI Scale потрібен повний кадр із відомим viewport.

Після дозволу реалізації етапу 1 перевірити в грі:

- GUI Scale **1, 2, 3, 4, Auto**, включно з фактичним scale, який гра допускає для малого вікна; стандартні, широкі та вузькі вікна, resize на відкритому E/B/editor.
- Цілі координати/масштаб, nearest sampling, відсутність поворотів, без стискання тексту дробовим transform. Якщо кіт не вміщається — переносити/використовувати погоджений компактний варіант, не зменшувати мовчки.
- Ліва/права рука, offhand, обидва attack indicator modes та off; збережені HUD positions/scale, reset, повторний запуск.
- Survival/creative/spectator, mount, плавання, повний набір HP/food/air/armor states, низька духовність, усі 22 акценти й невідомий/відсутній шлях.
- Кілька bossbars, ефекти й коротка тривалість, довгі server title/actionbar/scoreboard/Tab header-footer, чат із прокруткою, тости, субтитри; F1/F3, pause/sleep/death.
- Перемикач «ванільний / мод», перезапуск, F3+T, користувацький resource pack вище/нижче, відсутні/помилкові ресурси, українські glyphs. Ванільний режим повертає оформлення нижчих packs, не скидає config користувача.
- Сумісність із реально встановленими модами HUD/інвентарів, зокрема їхні резерви висоти й області слотів. Не заявляти сумісність з усіма довільними модами без перевірки.
- Профіль рендера: статичні PNG/9-slice в атласі, без генерації PNG/перезбирання atlas/читання JSON на кадр. Витяг видимого GUI щокадру лишається нормальною роботою Minecraft; «без зайвого перемальовування» не означає пропускати оновлення живих значень.
- Немає серверних пакетів, змін атрибутів/балансу/світів. Гру для аудиту не запускали; майбутні тести зі змінами стану — в окремому тестовому світі.

## 11. Послідовність погоджень

1. **Зараз: аудит.** Користувач погоджує повноту переліку й технічні межі.
2. **Дизайн-кит.** Окремий перегляд і підтвердження.
3. **Ескізи.** А/Б/В, стани й запрошені екрани; окремий вибір та «затверджую» для конкретної реалізації.
4. **Реалізація етапу 1.** Тільки погоджений HUD, локальний перемикач на B та потрібне застосування спільного кіту до вже погоджених наших поверхонь.
5. **Перевірка користувачем у грі.** Не починати етап 2 до її результату й дозволу продовжити.
6. **Етап 2.** Погоджені інвентарі/контейнери й компоненти. Перетин зі спільними віджетами меню узгоджується явно.
7. **Етап 3.** Лише за окремим рішенням користувача.

Поточний результат — інвентаризація і технічний план. Візуальний вибір, абсолютну сумісність та перевірку в грі цей аудит не підміняє.
